01

Why Dense Alone Falls Short

Dense retrieval encodes global semantics but loses lexical specificity. A query for "CVE-2024-1234" or "errno ENOSPC" or a product SKU will fail completely against a dense index if those exact strings were not seen in the training distribution — the model has no way to generalise a random identifier it has never encountered.

Where dense fails

  • Rare named entities (CVE IDs, part numbers, chemical formulae)
  • Exact keyword search (“the exact phrase” contract language)
  • New vocabulary added after training cutoff
  • Code identifiers (NullPointerException, API endpoint paths)
  • Highly technical jargon in specialised domains

Where BM25 fails

  • Paraphrase and synonym queries (“car” vs “automobile”)
  • Multilingual queries over an English corpus
  • Long-context semantic matching
  • Abstractive questions (“What causes X?”)
  • Queries shorter than 3–4 words with common terms
Empirical evidence

On the BEIR benchmark, BM25 achieves NDCG@10 of 31.7 averaged across 18 datasets. Top dense bi-encoders (BGE-M3, E5-mistral) achieve ~44–48. But on the Signal-1M (news tweet retrieval), FEVER (fact verification), and DBPedia tasks, BM25 still beats many bi-encoders. Hybrid consistently achieves 48–52 — a 5–10% relative gain over either alone.

02

BM25 — Mechanics, IDF, Length Normalisation

BM25 (Best Match 25, Robertson & Walker 1994) is still the default sparse baseline in 2025. Understanding its parameters prevents misuse.

BM25 scoring formula

For query Q with terms q𝑖 and document D:

score(Q,D) = ∑ IDF(q𝑖) × [tf(q𝑖,D) × (k₁+1)] / [tf(q𝑖,D) + k₁ × (1 − b + b × |D|/avgdl)]

where tf is term frequency in D, |D| is document length in tokens, avgdl is average document length, k₁ controls term-frequency saturation (typical: 1.2–2.0), and b controls length normalisation (typical: 0.75).

Hybrid Fusion — RRF, Score Normalisation, Weighted Sum

Once you have two (or more) ranked lists — one from BM25, one from dense — you need a fusion strategy. The three main approaches differ in robustness and tunability.

Reciprocal Rank Fusion (RRF)

Score = ∑ 1/(k + rank𝑖) where k=60 is the smoothing constant. No score calibration needed — only rank positions. Extremely robust to score-scale differences between retrievers. Default choice for most hybrid RAG systems. Implemented natively in Elasticsearch 8.9+ and Qdrant 1.7+.

Score normalisation + weighted sum

Normalise each retriever's scores to [0,1] (min-max or softmax), then combine: α × dense_score + (1−α) × sparse_score. Allows tuning the weight α for your domain — technical corpora often need α=0.3 (more BM25 weight). Sensitive to score distribution shifts between queries.

Learned fusion

Train a small MLP or LambdaMART model to weight the retrievers based on query features. Used in Bing, Google, and enterprise search systems. Requires labelled query–document pairs. Rarely justified for a single-domain RAG system — RRF is within 1–2 NDCG points of a tuned learned fusion at zero training cost.

RRF fusion in Python (retriever results as lists of doc IDs)
from collections import defaultdict
from typing import List, Dict

def rrf_fusion(
    ranked_lists: List[List[str]],
    k: int = 60,
) -> Dict[str, float]:
    scores: Dict[str, float] = defaultdict(float)
    for ranked in ranked_lists:
        for rank, doc_id in enumerate(ranked, start=1):
            scores[doc_id] += 1.0 / (k + rank)
    return dict(sorted(scores.items(), key=lambda x: x[1], reverse=True))

Cross-Encoder Rerankers — BGE-Reranker, Cohere Rerank, mxbai

Cross-encoders achieve higher relevance precision than any bi-encoder because the query and document tokens attend to each other inside the encoder. The cost is O(k) forward passes per query where k is the candidate set size.

BGE-reranker-v2-m3 via sentence-transformers CrossEncoder
from sentence_transformers import CrossEncoder

reranker = CrossEncoder(
    "BAAI/bge-reranker-v2-m3",
    max_length=512,
    device="cuda",
)

pairs = [(query, doc) for doc in candidate_docs]
scores = reranker.predict(pairs, batch_size=64)

reranked = sorted(
    zip(candidate_docs, scores),
    key=lambda x: x[1],
    reverse=True,
)[:top_k]
Truncation is a silent quality killer

Cross-encoders have a token budget (typically 512 tokens for BERT-based models). If query + document exceeds this, the document is truncated. For long passages (>300 tokens), use a chunk-and-max strategy: split the document into overlapping windows, score each window independently, take the max score. This adds latency but recovers 3–5 NDCG points on long-document corpora.

ColBERT as a Reranker — PLAID and Late Interaction at Scale

ColBERT (covered in Deck 01) can serve dual purpose: as the first-stage retriever (requires token-level index) or as a late-interaction reranker over a short-list of bi-encoder candidates. Used as a reranker, it has cross-encoder-level quality with 3–5× lower latency for k=100.

PLAID (Performance-optimised Late Interaction Driver) extends ColBERTv2 with centroid-based candidate pruning. For reranking over a pre-filtered short-list, you can skip the PLAID indexing step and run MaxSim directly on GPU in <50 ms for k=200.

# Rerank a pre-retrieved list (query, list of passage strings)
results = reranker.rerank(
    query="transformer attention mechanism",
    documents=candidate_passages,   # list[str], len <= 1000
    k=10,
)
# Returns list of {"content": str, "score": float, "rank": int}
When to choose ColBERT vs cross-encoder reranker

ColBERT reranker wins when: (1) candidate list is large (k>200), (2) you have GPU available, (3) you need to stay open-source. Cross-encoder wins when: (1) you need the absolute best MRR on a small k (≤50), (2) you can tolerate higher latency, (3) you want a managed API (Cohere). For most production pipelines: bi-encoder top-100 → ColBERT reranker top-20 → LLM with top-5 is a strong default cascade.

Multi-Stage Cascades — Recall vs Precision Per Stage

Every stage in a retrieval cascade has a different objective. Confusing recall (don't miss relevant docs) at stage 1 with precision (don't include irrelevant docs) at stage 3 is the most common architectural mistake in RAG pipelines.

The recall ceiling problem

If stage 1 misses a relevant document, no downstream stage can recover it. Therefore: optimise stage 1 for recall, not precision. A Recall@100 of 92% means 8% of user queries will have the answer in positions 101+ — invisible to the reranker. Monitor Recall@100 on a labelled evaluation set before tuning any downstream stage.

Latency Budgets — Where Reranking Fits in < 500 ms

A user-facing RAG endpoint must complete end-to-end in <500 ms for interactive use. The retrieval pipeline typically needs to stay within 200 ms to leave budget for LLM generation.

Parallelise BM25 + dense retrieval

BM25 and dense ANN searches are independent — run them in parallel using asyncio.gather or a thread pool. This collapses two ~20 ms operations into one. Fusion then adds <1 ms. Total stage-1 time: ~25 ms instead of ~40 ms. If you use Weaviate or Elasticsearch's built-in hybrid, the parallelism happens server-side automatically.

Eval — Recall@k, MRR, NDCG, Manual Review

Retrieval evaluation is distinct from generation evaluation. You need a labelled test set with known relevant documents per query.

Building a labelled test set without annotation teams

Use LLM-generated queries: for each document chunk, prompt a model to generate 3–5 questions that the chunk answers. The (question, chunk) pair is a positive label. Negative labels: pick chunks with BM25 rank 10–30 for the same query (hard negatives). 500–1000 pairs is sufficient for reliable Recall@10 and NDCG@10 estimates. Validated against human-labelled subsets in BEIR, this approach yields within 2–3% of human label quality.

09

What to Take Away

  • Dense retrieval alone fails on rare tokens and exact keywords. Always combine with BM25 unless your entire corpus is paraphrase-friendly prose.
  • RRF with k=60 is the default fusion strategy. It requires no score calibration and is within 1–2 NDCG of tuned weighted fusion.
  • Cross-encoder rerankers (BGE-reranker-v2-m3, Cohere Rerank 3.5) add 5–10 NDCG points over bi-encoder-only retrieval at the cost of 80–200 ms extra latency for k=100.
  • ColBERT reranker is the best latency-quality trade-off for k>100 on GPU. RAGatouille wraps colbertv2.0 for drop-in use.
  • Recall@100 at stage 1 is the ceiling. Measure it before tuning any downstream stage. A 90% ceiling means 10% of answers are permanently unreachable.
  • Parallelise BM25 + dense ANN. They are independent operations; serial execution wastes 20–30 ms on every query.
  • Cross-encoder truncation at 512 tokens silently degrades quality on long passages. Use chunk-and-max for documents > 300 tokens.
